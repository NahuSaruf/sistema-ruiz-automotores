# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All commands run from the `project/` directory (the actual app root — `package.json` lives here, not at the repo root).

- `npm run dev` — start the Vite dev server
- `npm run build` — production build (outputs to `dist/`)
- `npm run preview` — serve the production build locally
- `npm run lint` — ESLint over the whole project
- `npm run typecheck` — `tsc --noEmit` using `tsconfig.app.json`

There is no test runner configured in this project (no test script, no test files).

## Project origin

This app was scaffolded and is still edited via [bolt.new](https://bolt.new/~/sb1-iqrfixwd) (see `.bolt/config.json`, `.bolt/prompt`). Per `.bolt/prompt`, the standing UI conventions are: Tailwind CSS for styling, `lucide-react` for all icons, and avoid adding new UI/icon/theming packages unless truly necessary.

## Architecture

This is a single-page React + TypeScript + Vite app for "Ruiz Automotores" (a Renault dealership plan-de-ahorro / financing management portal), in Spanish. There is no router — `src/App.tsx` is a monolithic component that switches between views via local `useState`, and also inlines several modals (contact, benefits, model catalog, version spec sheets) directly in JSX rather than as separate components.

**View model (`App.tsx`):** a single `view` state (`'home' | 'user' | 'cliente' | 'admin' | 'nuevo'`) drives which top-level screen renders. Login is a single free-text field: typing `ADMIN` (or the "Acceso Admin"/bottom-nav "Admin" buttons) just navigates to `view === 'admin'` — it no longer grants access by itself. Any other input is looked up asynchronously via `buscarClientePorConsultaConNube` (Supabase first, falling back to `localStorage`) and routes to the client dashboard with whatever `ClienteCartera` match (or `null`) comes back.

**Admin authentication (`App.tsx`, `src/lib/supabase.ts`, `supabase/schema.sql`):** rendering `view === 'admin'` shows `<DashboardAdmin />` only if `adminAutenticado` is true; otherwise it shows a login form, regardless of how the user navigated there — this is the actual access gate, not the old `ADMIN` text check. When `nubeConfigurada`, it's a real Supabase Auth email/password form (`iniciarSesionAdmin` → `supabase.auth.signInWithPassword`); session state is tracked via `obtenerSesionAdminActual`/`suscribirseASesionAdmin` (wrappers around `supabase.auth.getSession`/`onAuthStateChange`) so a page reload or a login in another tab stays in sync. Whether an authenticated user can actually write is enforced server-side by Postgres RLS, not by this client code: `supabase/schema.sql` has an `admins` allowlist table (`user_id` → `auth.users.id`, populated by hand via SQL — there's no signup UI) and an `is_admin_ruiz()` `security definer` function that RLS policies on `cartera_clientes`/`adjudicados` check for all INSERT/UPDATE/DELETE; SELECT stays open to `anon` because the client's own self-service lookup has no auth. When `!nubeConfigurada`, the form instead falls back to a single shared password compared against `VITE_ADMIN_FALLBACK_PASSWORD` (see `.env.example`) — deliberately fail-closed (disabled if that var is unset) since it's a plaintext value inlined into the JS bundle, not real authentication; don't treat it as a security boundary.

**Two dashboards sharing data through localStorage + optional Supabase:**
- `DashboardAdmin.tsx` — staff-facing, tabbed (`activeTab`: `cartera` | `operativo` | `precios` | `licitaciones` | `estadisticas`). Admin uploads Excel/CSV files (via `xlsx` + `src/utils/excelParser.ts`) across the Cartera tab's sub-tabs: "Cartera General" (client roster), "Adjudicados" (SAP award report), plus the "Licitaciones" tab, which holds two independent uploads: "5 mejores ofertas" (bidding-history report) and "Grupos Invitados Acto `<N>`" (real monthly invited-to-bid list — see below). Each dataset is parsed client-side, deduped/merged via `combinar*ConConteo` helpers, and persisted to `localStorage` (`cartera_general_ruiz`, `adjudicados_ruiz`, `mejores_ofertas_ruiz`, `grupos_invitados_ruiz`). If Supabase env vars are set, saves also upsert to the cloud (`guardarCarteraEnNube`/`guardarAdjudicadosEnNube`/`guardarGruposInvitadosEnNube` — `MejorOferta`/"5 mejores ofertas" is the one dataset in this tab with **no** cloud sync, localStorage-only, a pre-existing gap) and on mount the admin panel pulls cloud data and merges it into localStorage (cloud wins on conflict — see `fusionarPorGrupoOrden` in `DashboardAdmin.tsx`; `grupos_invitados` merges by the composite `combinarGruposInvitadosConConteo` instead, since its identity is acto+grupo_orden, not grupo_orden alone). The `precios` tab ("Gestión Comercial & Precios") edits the centralized vehicle catalog described below.
- `DashboardCliente.tsx` — client-facing self-service portal. Reads the same `localStorage`-backed data (via `App.tsx`'s login lookup) to personalize the profile header, and independently reads `cargarMejoresOfertas()` for the client's bidding history, plus its own `AdjudicadoSAP` record (`cargarAdjudicados().find(a => a.grupoOrden === grupoOrden)`) to power a "Cambio de Modelo en tu Adjudicación" card: shown only when `identificarFamilia(modeloSuscripto) !== identificarFamilia(modeloAdjudicado)` (both resolving to one of the 9 tracked families — an unrecognized model name never counts as a mismatch) — i.e. only when the client's originally-subscribed model family actually differs from what they were adjudicated, meaning their model wasn't available that act. Deliberately doesn't try to list "compatible alternative models": the real "Particularidades Carta Vigencia" data doesn't support that at the family granularity this app works at (see below) — almost every subscribed family turns out permissive toward almost every other, so that list would carry no real signal. `grupoHabilitadoLicitacion` (gates the "Oferta Rápida de Licitación" button and Rombito's "¿Cómo licito?") is resolved from the real `grupos_invitados` data: it's `true` only if the client's `grupoOrden` appears in the **most recent `acto`** present in that dataset (an invitation from a past, already-closed act doesn't count forever) — see `invitacionVigente`/`actoMasRecienteInvitados`, refreshed on mount via a targeted per-`grupoOrden` Supabase query (`buscarGruposInvitadosPorGrupoEnNube`, not the whole table) so a client on a fresh device still gets a correct answer. The "Última Invitación del Grupo" card shows that same real acto/fecha/modelo when found. Also renders "Rombito", an inline rule-based chat widget (not backed by any LLM) with an identity gate (DNI or "Grupo y Orden" must match a regex before any query is answered), keyword-based intent tagging (`clasificarIntencion`/`responderRombito`) that picks a canned reply per department, business-hours-aware suffixes, and `!`-prefixed staff-only secret commands (`!broker`, `!fabrica`) that bypass the identity gate. Four quick-reply buttons (vencimiento, Puntos Ruiz, sucursales, licitar) skip that generic classifier: `respuestaAccesoRapido` matches their exact question text and answers with the same hardcoded values shown elsewhere on this same screen (e.g. `PROXIMO_VENCIMIENTO_FECHA` is shared with the "Estado de Cuenta" card so they can't drift), and the "¿Cómo licito?" one is an action, not a reply — it calls the `onIrALicitaciones` prop (wired in `App.tsx` to open `ModalOfertaLicitacion`) instead of pushing chat text. All of this logic lives inline in `DashboardCliente.tsx` — there is no separate `RombitoChat.tsx` component (an earlier, unused duplicate of this widget was removed as dead code).

**`src/utils/excelParser.ts`** is the canonical Excel-ingestion and persistence layer. It normalizes SAP-style export column names (many possible header spellings per logical field, matched case-insensitively via `buscarValorColumna`) and status strings (`normalizarEstadoSAP`) into clean shapes (`ClientePlan`, `ClienteCartera`, `AdjudicadoSAP`, `MejorOferta`, `GrupoInvitado`), owns their `localStorage` read/write/merge functions, and also does bidirectional SAP-code ↔ display-name translation (`traducirModeloSAP` for the admin/technical view, `formatearModeloCliente` for the simplified client-facing view) via the `MAPPING_MODELOS_SAP` table. When adding new spreadsheet-derived fields, extend this file's column-alias lists and mapping tables rather than special-casing parsing elsewhere. `procesarGruposInvitados` (real "Grupos Invitados Acto `<N>`" report) is the one parser here that doesn't assume a fixed header row index — the real file has a variable number of title/date rows before the actual column headers, so it locates that row by finding the one containing a `CONTRATOPR` cell (the Grupo y Orden column) rather than indexing `filas[0]`.

**`src/lib/supabase.ts`** creates the Supabase client only if `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are set (see `.env.example`); otherwise `supabase` is `null` and every exported function degrades to a no-op/`null` return, so the app always keeps working purely off `localStorage`. All cloud calls are wrapped in try/catch and never throw. `nubeConfigurada` is the boolean flag components check before showing cloud-related UI. It also exports the admin-auth wrappers used by `App.tsx` (`iniciarSesionAdmin`, `cerrarSesionAdmin`, `obtenerSesionAdminActual`, `suscribirseASesionAdmin`) — see the "Admin authentication" note above.

**CCA market-stats scraping (`api/cca-stats.ts`, `src/services/ccaService.ts`, `src/utils/estadisticasMercado.ts`):** the "Mercado Nacional" tab in `DashboardAdmin.tsx` shows national savings-plan market statistics sourced from `cca.com.ar/estadisticas/`, a page that renders its numbers client-side and sends no CORS headers. `api/cca-stats.ts` is a Vercel serverless function (memory/duration configured in `vercel.json`) that drives headless Chromium (`puppeteer-core` + `@sparticuz/chromium`) to load that page, click through its 4 sub-tabs (Suscripciones, FC, Conversión, Mercado Total), and regex-parse the already-rendered text — it returns an explicit error instead of fabricating data if CCA's markup no longer matches. It also supports `?debug=1` / `?debug=<TabName>` to dump a tab's raw rendered text, for re-deriving those regexes if CCA's layout changes. `src/services/ccaService.ts` is the browser-side client: it calls that same-origin endpoint, caches the last successful result in `localStorage` (`cca_stats_cache`, with a shape check that discards incompatible older cache formats), and never throws — callers fall back to the cache on any failure. `src/utils/estadisticasMercado.ts` holds a hand-recorded static snapshot used as the initial/fallback view before any live sync has run.

**Gestión Comercial & Precios — centralized vehicle catalog (`src/utils/condicionesComerciales.ts`):** this is the single source of truth for commercial data on all 9 model families (`CATALOGO_VEHICULOS_DEFAULT`, keyed `KWID`/`KARDIAN`/`DUSTER`/`BOREAL`/`KANGOO`/`OROCH`/`MASTER`/`ARKANA`/`KOLEOS`) — precio de lista, ficha técnica (motor/transmisión/tracción/consumo/baúl/equipamiento), bonificación/vigencia, and a **list** of financing plans (`ConfiguracionVehiculo.planes: PlanFinanciacion[]`) — plus the promo banner copy (`tituloPromo`/`descripcionPromo`). A model routinely has 2-3 plans live at once (confirmed against real Plan Rombo documents, e.g. Kardian at 100%/120c, 75%/120c and 75%/84c simultaneously); `modalidadPct`/`plazoCuotas` are plain numbers (not a fixed union), since real data isn't limited to a small fixed set. `planDestacadoIndex` picks which entry of `planes` is "the" plan shown in the Vitrina/Estado de Cuenta — `obtenerPlanDestacado(vehiculo)` resolves it (falling back to index 0, or `null` if the model has no plans at all). `cargarCondiciones()`/`guardarCondiciones()` read/write the whole `CondicionesComerciales` object as one JSON blob under `localStorage` key `condiciones_comerciales_ruiz`; the load merges per-vehicle and per-field against `CONDICIONES_DEFAULT` (including `planes`/`planDestacadoIndex`) so an older saved blob, or one missing a model/field entirely, can't leave `undefined` where code expects an array. **Nothing in the app ever resets or recomputes these values on its own** — they stay exactly as last saved until an Administrador edits/uploads again from `DashboardAdmin.tsx`'s "Gestión Comercial & Precios" tab (per-model form, one model selected at a time via `modeloSeleccionado`/`vehiculoEditado`; `planes` are edited as a list — add/edit/remove/mark-destacado per entry). Saves write to `localStorage` and, if `nubeConfigurada`, upsert to Supabase (`guardarCondicionesEnNube`, table `condiciones_comerciales`, a single row `id=1` holding the whole object as `jsonb`; RLS: open read, `is_admin_ruiz()`-gated write — see `supabase/schema.sql`). `App.tsx` and `DashboardCliente.tsx` each hold their own `condiciones` state seeded from `cargarCondiciones()`, refreshed on mount from Supabase directly (`obtenerCondicionesDeNube`, so a client on a fresh device sees real prices, not just the default snapshot) and kept live via the cross-tab `storage` event. Every place that used to hardcode a price/cuota/ficha técnica now derives it from this same object via `obtenerPlanDestacado`: `App.tsx`'s `vitrinaComercial` ("Quiero mi 0km" cards + detail pop-up, via the `datosComercialesVitrina(familia)` helper) and its `versionesPorModelo` `useMemo` (overrides only each family's "principal" version — see `VERSION_PRINCIPAL_POR_FAMILIA` — inside the richer static `VERSIONES_POR_MODELO_BASE` catalog, leaving other trims/versions per family untouched), and `DashboardCliente.tsx`'s "Estado de Cuenta" Plan Suscripto line plus its `CARACTERISTICAS_KARDIAN` ficha técnica (both read `condiciones.vehiculos.KARDIAN`).

**Ingesting the real "Lista de Precios RED" Excel (`procesarListaPreciosRed` in `condicionesComerciales.ts`):** Plan Rombo's actual monthly price list isn't a flat table — it's a sequence of per-combo "blocks" (one per modelo+modalidad+plazo, e.g. "Kardian 75% en 84 cuotas"), each with several label/value rows beneath a header row matched by the regex `RE_BLOQUE` (`"<N> cuotas | modalidad <N>%"`, found by scanning columns B–I since the exact column shifts slightly between models). Within a block (up to the next block's header row), the parser looks up rows by exact label text — `"> Versión"` and `"Cuota Desde"`/`"Precio público"` — never by fixed column position for the row itself. A block missing a Versión or a Cuota Desde is dropped entirely rather than saved half-populated. `identificarFamilia` maps the block's free-text model label (`"Kardian Evolution"`, `"Kangoo Stepway"`, `"Kangoo 2A"`, `"Kangoo 5A"`, ...) to one of the 9 tracked families by substring match after accent-stripping (`normalizarTexto`) — note all three Kangoo body styles fold into the single `KANGOO` family. `combinarPlanesDesdeRed(vehiculos, planesPorFamilia)` **replaces** (doesn't append to) each detected family's `planes` array — a price list is a full monthly snapshot, not an incremental update — and resets `planDestacadoIndex` to 0; families the file doesn't mention are left untouched. `DashboardAdmin.tsx`'s upload button for this (in the Gestión Comercial & Precios tab) saves immediately (localStorage + Supabase) on success, same as the other file uploads in this panel, rather than requiring a separate manual save click.

**Ingesting the "Lista de Precios" (raza) Excel (`procesarListaPreciosRaza`/`combinarPrecioListaDesdeRaza` in `condicionesComerciales.ts`):** a *different*, flatter Renault document than RED — one MSRP per individual trim/version across the whole lineup (broader coverage than RED, e.g. it's the only one of the two with Arkana/Koleos prices), grouped under section-header rows containing only the family/line name (column C) with an empty "Código de Modelo" (column D); data rows have that column D filled and carry `Versión` (column G) + the final "Público con impuestos nacionales" price (column M). The parser walks rows top-to-bottom tracking "current familia" from the last section header seen, resolved through the same `identificarFamilia`. Only `precioLista` is ever touched — `planes`/ficha técnica are untouched. Per family, `combinarPrecioListaDesdeRaza` prefers the trim whose name matches (accent/case/whitespace-insensitive) an existing plan's `version` (from a prior RED upload — the most trustworthy price, since it's for the exact version being financed) and falls back to that family's cheapest listed trim otherwise; it never averages or fabricates a number, and the admin UI lists which trim/price got picked per family (and whether it was a plan match or the fallback) so nothing is silently guessed.

**Ingesting "Particularidades Carta Vigencia" (`procesarDisponibilidadVersiones` in `condicionesComerciales.ts`, stored as `CondicionesComerciales.disponibilidadVersiones: DisponibilidadVersion[]`):** the real file is a "modelo suscripto" (columns) × "modelo pedido" (rows) matrix with an "a" mark per enabled cell — but empirically, almost any subscribed family enables almost any other at the family granularity this app works at, so this parser deliberately **doesn't** build that cross-matrix. It only extracts, per individual trim/version row, whether it has *any* mark at all across every column — i.e. whether that version is orderable this month, independent of what was originally subscribed (confirmed against the real file: exactly one trim, "Kardian Techno 200 DCT", had zero marks that month vs. every other trim being fully enabled). Row detection: a row is a family section header (not a version) only if `Cód. Ind.` (column A) is empty **and** every matrix column (C onward) is also empty — checking column A alone isn't enough, since several real version rows (e.g. "Kangoo Express 2A 1.5 dCi 89") have no code but do have real "a" marks and must still be parsed as data. This is purely an admin reference table (Control Operativo tab, for staff doing manual "cambio de modelo") — it does **not** feed a client-facing "compatible alternatives" list (see the note on `DashboardCliente.tsx`'s substitution card above for why that was deliberately skipped).

**"Integración Mínima" data (`PlanFinanciacion.integracionMinimaPct`/`.cuotasIntegracionMinima`, both optional strings) has no parser at all — it's manually entered.** The two real Plan Rombo documents that carry it are an image (Integración Mínima) and a 30-page PDF (Política Comercial) whose relevant table gets mangled by naive text extraction (columns interleave); unlike every other real document integrated into this app, there's no reliable automated way to ingest either with the tools available here, so this stayed a manual field in the per-plan editor in `DashboardAdmin.tsx`'s Gestión Comercial & Precios tab instead of a fourth upload button. The values are free text (not numbers) because the real data isn't always a percentage — it can say `"cuota extra"` or `"-"` (not applicable). `CATALOGO_VEHICULOS_DEFAULT`'s default plans carry the real August 2026 values, hand-transcribed once from the image; Arkana/Koleos have neither field set because neither document covers those two models. Nothing recomputes or re-fetches these — same "never resets on its own" rule as the rest of `condicionesComerciales.ts`.

**`src/components/`** now contains only the files actually wired into the app: `DashboardAdmin.tsx`, `DashboardCliente.tsx`, `Header.tsx`, `LicitacionesCliente.tsx`, `ModalOfertaLicitacion.tsx` (plus everything inlined in `App.tsx`). The previously-orphaned components (`BaseClientes.tsx`, `Catalogo.tsx`, `ConsultarPlan.tsx`, `DashboardOperativo.tsx`, `Estadisticas.tsx`, `Footer.tsx`, `Hero.tsx`, `Login.tsx`, `MiCuentaModal.tsx`, `PortalCliente.tsx`, `RombitoChat.tsx`) and the unused `src/data/vehiculos.ts` were deleted as dead code — none of them were imported anywhere. When adding a new component, still verify actual imports before assuming something under `src/components/` is live, since nothing structurally prevents a new orphan from accumulating.

**Vehicle/model image assets** (`Boreal*.png`, `Duster*.png`, `Kangoo*.png`, `Kardian*.png`, `Koleos*.png`, `Kwid*.png`, `Master*.png`, etc.) live in `public/` and are referenced by root-relative paths (e.g. `/Kwid.png`). Numbered variants (`Duster Intens MT 1.png` … `...6.png`) are 360°-style rotation frames consumed by mouse/touch-drag interactions — see `VisorVersion360` in `App.tsx` (used by the model catalog's spec-sheet modal) and the equivalent inline 360° viewer in `DashboardCliente.tsx`. `dist/` is a committed build output mirroring `public/` — don't hand-edit files there; regenerate via `npm run build`.
